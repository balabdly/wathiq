# وثيق — ربط الفوترة الإلكترونية (فاتورة) المرحلة الثانية

> **الحالة:** تطوير وتجارب معزولة، وليس تفعيلًا إنتاجيًا أو شهادة مطابقة من هيئة الزكاة والضريبة والجمارك.

## المنجز برمجيًا

1. مسودة XML بتنسيق UBL 2.1 لفاتورة B2B القياسية بنسبة 15%، مع فحص بيانات الأطراف والبنود والإجماليات. **ليست XML مكتملة أو موقّعة تلقائيًا.**
2. أربع جداول معزولة لكل منشأة ووحدة EGS لحفظ حالات الفاتورة والتسلسل ICV والبصمة PIH وسجل الأحداث، مع حجز وإنهاء ذريين.
3. حماية RLS وصلاحيات خادمية فقط؛ لا تسمح الجداول بقراءة أو تعديل مباشر من المتصفح.
4. إصلاح أول PIH باستخدام القيمة الخاصة المحددة من الهيئة، وتجهيز التحقق من توقيعات secp256k1.
5. اختبارات PostgreSQL فعلية في GitHub Actions لحجز فاتورتين متزامنتين ومنع التكرار، وحماية بيانات الشركات وحفظ بصمة الفاتورة التالية.
6. بوابة خادمية للتوقيع والتأكد من سلامة XML باستخدام **أداة ZATCA الرسمية المثبتة منفصلًا**. ترفض التشغيل إذا لم تكن الأداة متاحة أو لم تُعلن PASS صريحًا.
7. بنية إرسال أولية لا تتصل إلا بعنوان **Simulation**؛ مع إيقاف الاتصال افتراضيًا، والتحقق من الرد الفعلي قبل اعتبار الفاتورة Cleared أو Reported.

## تشغيل SDK على بيئة اختبار معزولة

1. يُحمّل مشغّل النظام SDK الرسمي ودليل الاستخدام من:
   https://www.zatca.gov.sa/en/E-Invoicing/SystemsDevelopers/ComplianceEnablementToolbox/Pages/DownloadSDK.aspx
2. يُجهز بيئة اختبار منفصلة بمفتاح وشهادة **اختباريين** مطابقين للبيئة، دون وضع أي أسرار في GitHub أو كود المتصفح.
3. يحدد مشغّل الخادم هذه الإعدادات في بيئة تشغيل **خادمية** فقط (وليس NEXT_PUBLIC_):
   - `ZATCA_SDK_FATOORA_BIN`: المسار التنفيذي الصحيح لأداة `fatoora` الرسمية.
   - `ZATCA_SDK_WORKDIR`: دليل SDK المعزول الذي يقرأ منه إعدادات الاختبار.
   - `ZATCA_SDK_SIGNING_ENABLED=true`: للتجربة المحلية الآمنة فقط، ولا تُشغّل على بيئة الإنتاج.
4. يستعمل الجسر `fatoora -sign -invoice INPUT -signedInvoice OUTPUT`، ثم يُعيد فحص الناتج بالأمر `fatoora -validate -invoice FILE`. عدم وصول نتيجة **GLOBAL VALIDATION RESULT - PASSED** يُوقف العملية.
5. تنتهي الملفات المؤقتة بالحذف، ولا تُعيد واجهات الجسر مخرجات SDK التي قد تحتوي على بيانات فواتير أو أسرار.

> هذه الأوامر لم تُنفّذ حتى الآن ضد SDK الرسمي، لعدم تهيئة ملفاته وشهادات الاختبار في GitHub Actions. اختبارات البرنامج الحالية تختبر الحماية ومنطق البوابات باستخدام محاكاة، **ولا تساوي فحص SDK الحقيقي**.

## الربط التجريبي

المسارات المحضرة:
- `/e-invoicing/simulation/invoices/clearance/single` للفواتير القياسية.
- `/e-invoicing/simulation/invoices/reporting/single` للفواتير المبسطة.

الاتصال **معطّل** افتراضيًا، ولا يفعّله مجرد وجود شهادة. عند اكتمال توقيع فاتورة تجريبية والتحقق الرسمي من XML، تُضبط إعدادات الخادم الخاصة بالاختبار:
- `ZATCA_SIMULATION_NETWORK_ENABLED=true`
- `ZATCA_SIMULATION_BINARY_SECURITY_TOKEN`
- `ZATCA_SIMULATION_SECRET`

هذه البيانات تُحفظ في مخزن الأسرار المخصص ولا تُكتب في قاعدة البيانات أو المستودع. لا يوجد في المشروع مسار يستخدم رابط Production `/e-invoicing/core`.

## شروط منع التفعيل الرسمي

- بناء XML الموقّع كاملاً حسب أحدث متطلبات UBL وXAdES وC14N11، والتحقق منه عبر SDK **حقيقي**، مع عينات فواتير متنوعة.
- تشغيل شهادة اختبار ونجاح طلبات Compliance وClearance وReporting على بيئة الهيئة التجريبية، مع فحص الإشعارات الدائنة والمدينة وبدلات الدفع المقدم والتوريدات غير القياسية.
- إدارة سرية لمفاتيح التوقيع والشهادات لكل شركة ووحدة فوترة (لا تحفظ المفاتيح الخام أو OTP في سجلات وثيق).
- حفظ الملف الموقّع ورد الهيئة في مخزن خاص مع ضمان توافرهما **قبل** تحديث حالات المستند؛ الدالة الحالية تقبل مسار الملف من الخادم ولا تتحقق من وجوده فعليًا في التخزين.
- ربط عمليات التوقيع والتخزين والإرسال وإعادة المحاولة بآلية idempotency وحالات قابلة للمطابقة والتدقيق؛ لا يكفي اعتبار HTTP 200 دليلاً على القبول.
- اجتياز فحوص TypeScript والاختبارات والبناء وESLint، ثم تفعيل الترحيل رسميًا بعد اعتماد الإعدادات وشهادات الهيئة.

**لا تُطبّق جداول EGS في قاعدة الإنتاج أو تُدمج المسودة #11 لمجرد اجتياز اختبارات البنية.**
